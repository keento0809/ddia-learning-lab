## 1. 決定事項の要約

| # | 論点 | 決定 |
|---|---|---|
| D-1 | 内部API | service bindingによる隔離に加え、アプリケーション層でも呼び出し元を認証する |
| D-2 | 認証の試行制御 | 発信元単位と対象アカウント単位の制限を組み合わせ、Bot対策を併用する |
| D-3 | セッション | JWT戦略を維持し、サーバ側で無効化できる仕組みを追加する |
| D-4 | 本人確認 | メール基盤の導入を前提に、パスワードリセットとMFAを段階的に提供する |
| D-5 | 依存関係の追従 | 新しい版の待機、定期的な検査、許容の根拠と解消条件の明記を標準とする |

## 2. 内部API(D-1)

### 背景
09_ADR-008は、worker-apiに公開ルートがないことを前提に内部エンドポイントを設計した。この前提は引き続き有効だが、デプロイ設定や転送処理の誤りが直ちに認証の境界へ影響するため、単一の防御層に依存しない構成へ改める。

### 決定
- 内部エンドポイントは、worker-appだけが持つ秘密情報による認証を必須とする
- 比較は定数時間で行い、秘密情報が未設定の場合は拒否する
- クライアントが送った同名のヘッダは転送しない
- 公開APIの転送経路と内部APIの呼び出し経路は分離したまま維持する

### 移行
worker-apiが先にデプロイされるため、受け入れと強制を2段階に分け、移行中に認証を停止させない。

## 3. 認証の試行制御(D-2)

- 発信元単位の制限は維持する
- 対象アカウント単位の制限を追加する。キーには生のメールアドレスを使わない
- ログイン応答は、アカウントの有無で区別できない形に揃える
- 公開フォームにBot対策を導入する。導入時はCSPと既存のセキュリティ記録を更新する
- 認証以外の状態変更APIにも利用者単位の制限を設ける
- 認証イベントの構造化ログと監視を先に整備し、制限の効果を観測できる状態で導入する

## 4. セッション(D-3)

- Auth.jsのJWT戦略は維持する
- worker-apiはリクエストごとにユーザーを照合しているため、その処理にセッション世代の照合を追加する
- ログアウト時に世代を更新し、発行済みトークンを無効化する
- `users`への列追加を伴うため、実装時に02 §2.1を更新する。テーブルは追加しない
- JWTの有効期限は既定値から短縮し、値は実装タスクで決定する

## 5. 本人確認(D-4)

- パスワードリセットは、メールアドレスの所有を証明できる配送経路を用意するまで無効のままとする
- メール基盤は実装タスクで選定する
- サインアップ時のメール確認は同じ基盤で導入し、その時点で登録済みメールの応答を見直す
- MFAはパスワードリセットの後に提供し、一般公開の範囲を広げる前に完了させる

## 6. 依存関係の追従(D-5)

| 項目 | 方針 |
|---|---|
| 採用する版 | 間接依存を含め、公開から14日以上経過した版を使う |
| 例外 | 判断者、理由、解消日を`docs/tasks/STATUS.md`に記録する |
| 検査 | CIで定期実行し、pushがない期間も新しいアドバイザリを検知する |
| 許容リスト | 実測した根拠と解消条件を記載し、解消済みの項目は削除する |
| メジャー更新 | 自動更新の対象外とし、個別タスクで移行と検証を行う |
| サポート期限 | 主要な依存の期限を追跡し、期限の前に移行を完了する |

## 9. 検討した代替案

| 案 | 不採用の理由 |
|---|---|
| service bindingの隔離のみを維持する | 設定や転送処理の誤りを防ぐ層がなくなる |
| DBセッションへ戻す | 09_ADR-008の設計を変更する範囲が大きく、世代の照合で要件を満たせる |
| 発信元単位の制限のみで対応する | 分散した発信元からの試行を抑えられない |
| 依存更新を即時に自動マージする | 公開直後の汚染版を取り込むリスクがある |
