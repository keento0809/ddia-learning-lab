# ADR-012: デザイントークンとスタイルガイド

| 項目 | 内容 |
|---|---|
| ステータス | Proposed (2026-08-21) |
| 背景となる事象 | スタイルガイド不在の調査により、デザイントークン・共通UIコンポーネント・スタイル規約のいずれも存在せず、ボタンのクラス文字列が31ファイルにコピペされドリフトが発生していることが判明 |
| 関連 | 01_基本設計書 §6.3(技術スタック: Tailwind CSS + Radix UI)、02_詳細設計書 §4(画面詳細)、11_ADR-010(CSP: 外部リソース許可) |

---

## 1. コンテキスト

### 1.1 調査で判明した現状

| 観点 | 実態 |
|---|---|
| デザイントークン | **存在しない**。`tailwind.config.*` 自体がなく(Tailwind v4のCSS-first構成)、`@theme` ブロックでのカスタム定義もない |
| 共通UIコンポーネント | **存在しない**。`components/ui/` ディレクトリがなく、`<button>` タグが31ファイルに直書きされている |
| スタイル規約の文書 | **存在しない**。`docs/design/` にも `.claude/skills/` にも該当なし |
| 視覚カタログ | **存在しない**(Storybook等なし) |

唯一の一貫性は「Tailwindデフォルトの `neutral-*` パレットと `.dark` クラス戦略を惰性的に踏襲している」という**偶発的なもの**であり、明文化・強制された規約ではない。

### 1.2 既に発生している問題

- **primary buttonのコピペドリフト**: 同一の意図を持つクラス文字列が `SignInForm` / `SignUpForm` / `CompleteAndNextButton` / `LabToolbar` / `QuizInline` / `QuizQuestionCard` 等に複製され、`padding` や `disabled:opacity-{40,50,60}` が微妙に食い違っている
- **セマンティックカラーの不統一**: エラー色だけで `red-400` / `red-600` / `red-700` / `red-800` が混在。成功色も `emerald-400` / `emerald-700` 等が場当たりに選ばれている
- **生HEX値の直書き**: 5箇所(`#ccc` ×2、`#9ca3af` 等)
- **ダークモードのペア不統一**: 方式(`.dark` クラス)は統一されているが、`neutral-200/dark:800` と `neutral-300/dark:700` のように具体的な濃淡の組み合わせが揃っていない

### 1.3 なぜ今対処するか

06(並列実装戦略)に基づき複数タスクを同時実行する運用を続けている。**各タスクが「自分の担当箇所だけ、その場の判断でスタイリングする」状態が続くと、タスク数に比例して不統一が拡大する**。実際、直近のテーブルスタイル追加PRのコミットメッセージ自体が「共通の型指定手段がないため、他要素と同様に素のCSSで対応する」と、場当たり運用を自覚した上での判断を記録している。

## 2. 決定

### 2.1 ブランドカラーの基準: favicon

本アプリのfavicon(`public/icon.svg`)で採用した配色を、プロダクト全体のブランドカラーの基準とする。

| 用途 | 値 | 意味 |
|---|---|---|
| ブランドカラー(プライマリ) | `#38BDF8` | 分散システムのノード・接続を表す青。favicon の図形色 |
| ブランド背景(ダーク) | `#111827` | favicon の背景色。ダークテーマの基調 |

**faviconを基準にする理由**: プロダクトの視覚的アイデンティティは既にfaviconで確定しており、これとUIの配色が乖離するとブランド体験が分断される。また「どの色を選ぶべきか」という設計判断が不要になり、置き換え作業を機械的・並列的に進めやすくなる。

### 2.2 トークン体系

Tailwind v4の `@theme` ブロック(`app/globals.css`)でCSS変数として定義する。**依存パッケージの追加は行わない**(CLAUDE.md規則1に配慮)。

| カテゴリ | トークン | 用途 |
|---|---|---|
| **ブランド** | `--color-brand-{50..900}` | プライマリボタン、リンク、アクティブ状態、フォーカスリング |
| **セマンティック** | `--color-danger-*` | エラーメッセージ、削除操作、失敗状態 |
| | `--color-success-*` | 成功メッセージ、合格状態、完了表示 |
| | `--color-warning-*` | 警告、注意喚起 |
| | `--color-info-*` | 補足情報、Callout(info) |
| **ニュートラル** | 既存の Tailwind `neutral-*` を継続使用 | 本文、境界線、背景。既に一貫しているため変更しない |

セマンティックカラーはブランドカラー(青)との調和を考慮して選定する。各トークンはライト/ダーク両方の値を持つ。

### 2.3 共通UIコンポーネント

`components/ui/` を新設し、少なくとも以下を共通化する:

| コンポーネント | 集約対象 |
|---|---|
| `Button` | 31ファイルに散在する `<button>`。variant(primary/secondary/danger)、size を props で制御 |
| `Card` | `rounded border border-neutral-* p-4` 系のパターン(quiz/lab/viz/mdx に散在) |
| `FormField` | 入力欄+ラベル+エラー表示のパターン(auth/settings) |

既存の Radix(`@radix-ui/react-dropdown-menu`)は継続利用し、必要に応じて他のRadixプリミティブを追加する(01 §6.3 の技術スタック方針に沿う)。

### 2.4 文書の役割分担

| 場所 | 役割 |
|---|---|
| **本ADR(docs/design/12)** | **なぜ**この配色・体系にしたか。移行方針。人間が設計判断を振り返るための記録 |
| **`.claude/skills/style-guide/`** | **どう書くか**。トークン名の一覧、Buttonのvariant一覧、使用例。実装タスクが参照する実務手順 |
| **`docs/tasks/STATUS.md`** | 移行の進捗と、個別タスクでの逸脱判断のログ |

## 3. 移行方針(段階的・一括置換はしない)

**既存の31ファイル・348箇所の `dark:` 指定を一度に書き換えることはしない。** 影響範囲が大きすぎ、予期しない見た目崩れの検証が困難になるため。

| Step | 内容 | リスク |
|---|---|---|
| **S1** | `@theme` にトークンを定義する(既存コード無変更) | 低。新規追加のみ |
| **S2** | `.claude/skills/style-guide/SKILL.md` を作成し、トークンとコンポーネントの使用規約を明文化 | 低 |
| **S3** | `components/ui/Button.tsx` を新設。**ブランドを象徴する箇所(ヘッダー・主要CTA)から**段階的に置き換え | 中。1画面ずつ実クリック確認 |
| **S4** | セマンティックカラーの置き換え(エラー/成功色の統一) | 中 |
| **S5** | `Card` / `FormField` の共通化 | 中 |

各Stepは独立したタスクとして起票し、**Step完了ごとに実表示を確認してから次へ進む**。

### 3.1 移行期間中のルール

- **新規に追加する視覚要素**は、その時点で利用可能な共通部品・トークンを使用する(未整備なら既存パターンを踏襲し、STATUS.mdに記録)
- **既存箇所を「ついでに」書き換えない**(CLAUDE.md規則1のスコープ限定に従う)
- 置き換えタスク以外で `components/ui/` や `@theme` を変更する必要が生じた場合は、理由を完了報告に明記する

## 4. 帰結

### 4.1 得られるもの

- 並列タスクが同じ参照点(トークン・共通部品)を持てるため、タスク数が増えても不統一が拡大しない
- ブランドカラー変更が必要になった際、トークン1箇所の修正で全体に反映される
- `Button` の挙動(disabled時の見た目、フォーカスリング等)を1箇所で保証でき、アクセシビリティの担保も容易になる

### 4.2 受け入れるコスト

- 移行タスク5件分(S1〜S5)の実装・検証コスト
- 移行期間中、新旧のスタイル指定が混在する期間が発生する
- Tailwindの生クラス直書きに比べ、`components/ui/` 経由は一段の間接参照が増える(ただしドリフト防止の利益が上回ると判断)

### 4.3 意図的に対象外とするもの

| 対象外 | 理由 |
|---|---|
| Storybook等の視覚カタログ導入 | 依存追加とビルド構成の変更を伴い、Cloudflare Workers環境(ADR-007/008のバンドル予算)への影響が読めない。必要性が生じてから再検討 |
| CSS-in-JSやデザインシステムライブラリの導入 | 同上。現在のTailwind v4 CSS-first構成で目的は達成できる |
| ニュートラルカラーの再設計 | 既に `neutral-*` で一貫しており、変更の利益がない |
