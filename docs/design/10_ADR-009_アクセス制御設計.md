# ADR-009: 未サインイン時のコンテンツアクセス制御(段階的ゲーティング)

| 項目 | 内容 |
|---|---|
| ステータス | Proposed (2026-08-01) — T-601スパイクの結果を受けてAcceptedに更新する |
| 背景 | 現状、サインイン有無にかかわらず全コンテンツが閲覧可能。01 §4 の F-17(ゲスト未ログイン体験: Part I 冒頭を認証なしで体験可)が未実装のまま全開放状態になっている |
| 関連 | 01 §4(F-09/F-10/F-17)、02 §4・§6(ゲスト進捗)、05 ADR-007(コスト構造)、09 ADR-008(2 Worker構成) |

---

## 1. 現状と問題

| 観点 | 現状 | 問題 |
|---|---|---|
| コンテンツ | 全12モジュール(実装済み分)が未認証で閲覧可 | 設計意図(F-17)からの逸脱。サインアップ動機がゼロ |
| 進捗/ノート/ダッシュボード | 認証必須(実装済み) | ここだけ守られている |
| API | worker-api がJWT検証済み(ADR-008) | データ層は問題なし |

つまり**データは守られているがコンテンツは全開放**という非対称な状態。原因はWBSにアクセス制御タスクが一件も存在しなかったこと(S-01/S-10と同じ計画漏れパターン)。

---

## 2. 一般的なパターンの検討

学習系サービスで採用される代表的な方式:

| パターン | 例 | 本件への適合 |
|---|---|---|
| **完全無料** | freeCodeCamp | ✗ アカウント作成動機がなく、進捗機能が活きない |
| **登録ウォール(サンプル無料)** | Coursera(聴講)、多くのSaaSドキュメント | **◎ 本件に最適**。試用→登録の導線が自然 |
| **メーター制(月N本まで無料)** | Medium | △ 実装が複雑(閲覧回数の匿名追跡)。学習教材では文脈に合わない |
| **完全ウォール(登録必須)** | 一部の有料スクール | ✗ 価値訴求前に離脱。SEOも死ぬ |
| **有料課金** | — | ✗ スコープ外(01 §2.2で対象外と定義済み) |

**採用: 登録ウォール(サンプル無料)。** 無料範囲で価値を体験させ、続きに登録を要求する。課金は行わないため、「登録=進捗保存が始まる」という交換条件が明快。

---

## 3. 決定: 無料/ゲート境界

### 3.1 アクセス階層

| 階層 | 対象 | 未サインイン |
|---|---|---|
| **Public** | ランディング(S-01)、カリキュラム一覧(S-02)、モジュール詳細(S-03)、用語集(S-08)、検索(S-09)、認証画面(S-11) | 全閲覧可 |
| **Free Tier** | **モジュール1(信頼性・スケーラビリティ・保守性)の全レッスン・クイズ・演習** | 全閲覧・実行可(進捗はlocalStorage) |
| **Preview** | モジュール2〜12の**各モジュール第1レッスンの冒頭のみ**(見出し2つ分 or 約30%) | 冒頭表示+ソフトウォール |
| **Gated** | 上記以外の全レッスン本文、全クイズ、全演習、可視化 | ソフトウォール(CTA表示) |
| **Auth Required** | ダッシュボード(S-07)、設定(S-10)、ノート、修了証(S-12) | サインインへ誘導(実装済み) |

**モジュール1を丸ごと無料にする理由**: 「1レッスンだけ読める」より「1モジュールを完走できる」方が価値の実感が強く、クイズ・演習という本アプリ固有の体験まで到達できる。F-17の「Part I冒頭」の解釈としても妥当。

### 3.2 ソフトウォールの仕様(Preview階層)

```
┌──────────────────────────────────┐
│ # レッスンタイトル                  │  ← 常に表示(SEO)
│ 導入段落…(冒頭30%)                │  ← 常に表示
│ ─────────── 徐々にフェードアウト ── │
├──────────────────────────────────┤
│  🔒 続きを読むには無料登録が必要です  │
│  ・全12モジュールの教材が読み放題      │
│  ・演習の実行と自動採点               │
│  ・学習進捗の保存とバッジ             │
│  [無料で登録]  [サインイン]           │
│  モジュール1は登録なしで全部読めます →│  ← Free Tierへの導線
└──────────────────────────────────┘
```

**ハードウォール(何も見せない)にしない理由**: SEOで検索流入を得るには本文の一部がインデックスされる必要がある。またユーザーが「何が得られるか」を判断できないと登録に至らない。

## 4. 実装方式の候補(T-601スパイクで実測して決定)

**重要**: 本アプリはSSG+静的アセット配信で無料枠運用が成立している(ADR-007)。ゲーティングの実装方式によってこのコスト構造が壊れうるため、**方式決定は実測を経てから行う**。過去にバンドルサイズを実測せず設計判断して失敗した反省を反映する。

| 方式 | 概要 | 懸念(実測すべき点) |
|---|---|---|
| **A: 動的レンダリング** | ゲート対象ルートを`force-dynamic`にし、worker-app内でJWT検証して本文の出し分け | ①worker-appのバンドルに全コンテンツが載り2.5MiB予算を超えないか ②Worker invocationが10万/日枠を圧迫しないか ③LCPが2.5s以内を維持できるか |
| **B: 静的プレビュー + 認証付きフェッチ** | ページ自体はSSG(冒頭のみ埋め込み)。本文はworker-api経由でJWT検証後に取得 | ①コンテンツ本体の置き場(worker-apiバンドルは2.5MiB予算があるためR2/KVが必要か) ②本文取得のレイテンシとちらつき ③実装複雑度 |
| **C: UI非表示のみ** | クライアント側で隠すだけ | ✗ 開発者ツールで容易に回避可能。**単体では採用しない** |

**評価基準(T-601で判定)**: ①両Workerのgzipサイズが予算内 ②主要3画面のLCP≤2.5s ③Worker invocation増加の見積もりが無料枠の50%以内 ④実装工数。

**なお本件はDRMではない**。教材は秘匿情報ではなく、目的は登録転換であって不正コピー防止ではない。**サーバ側で本文を返さない**レベルの実効性があれば十分で、暗号学的な堅牢性は求めない。この線引きにより過剰実装を避ける。

---

## 5. 多層防御(方式A/Bいずれでも共通)

| 層 | 責務 | 実装 |
|---|---|---|
| **1. サーバ(正)** | ゲート対象コンテンツを未認証に返さない | 選定方式に従う(A: 動的出し分け / B: worker-apiの認可) |
| **2. API** | 進捗・提出・ノートの書き込み拒否 | ADR-008で実装済み(JWT検証) |
| **3. 演習定義** | ゲート対象演習のテスト定義・テンプレートを未認証に渡さない | 演習YAMLの配信をゲート対象に含める(§6参照) |
| **4. UI** | ソフトウォール表示、ナビゲーションの出し分け | 表示上の配慮のみ(セキュリティ境界ではない) |

**層1が唯一の正**。層4だけで守った気にならないこと(方式Cを単体採用しない理由)。

## 6. 既存機能への影響

| 機能 | 影響 | 対応 |
|---|---|---|
| ゲスト進捗(T-113) | Free Tier(モジュール1)の進捗はlocalStorageに保存し、登録時にマージする既存動作を維持 | 変更不要。ただしゲート対象の進捗は発生しないことを確認 |
| 演習実行(T-108r) | ゲート対象演習はYAML自体を配信しない | 演習ルートもゲート対象に含める |
| 検索(T-306) | ゲート対象本文が検索インデックスに含まれると、スニペットで内容が漏れる | インデックスは**タイトル+要約のみ**に制限、または結果クリック時にウォール表示 |
| 可視化(T-204〜208) | ゲート対象レッスン内のVizは表示されない | ウォール表示に置き換え。`/viz-preview`系は開発専用のためnoindex維持(実装済み) |
| SEO | ゲート対象ページが薄いコンテンツと判定されるリスク | 冒頭+構造化データを出力。`robots.txt`でゲートページを除外しない(プレビューはインデックスさせる) |
| ダッシュボード(T-112) | 変更なし(既に認証必須) | — |

## 7. タスク分割(T-601〜T-605)

### T-601 方式選定スパイク(サイズM / 実装は最小限)
- 目的: §4のA/B方式をプロトタイプし、①両Workerのgzipサイズ ②LCP ③Worker invocation見積もり ④実装複雑度を**実測**して方式を決定する
- 成果物: 各方式の測定結果表、推奨方式と根拠、本ADRの§4への追記案(ファイル変更はせず提案のみ)
- 受入基準: 両方式で最小プロトタイプ(1レッスンのみ)を作り実測値を提示。数値なしの推測による推奨は不可
- **人間の判断ポイント**: 測定結果を見て方式を裁定してからT-602へ進む

### T-602 アクセス制御の基盤とサーバ側ガード(サイズL)
- 成果物: `lib/contracts/`にアクセス階層の型定義(module/lessonごとのtier判定関数)、選定方式に基づくサーバ側ガード、未認証時にゲート対象本文が**レスポンスに含まれないこと**の検証テスト
- 受入基準: 未認証でゲート対象URLを直接叩いた際のレスポンスbody/RSCペイロードに本文が含まれないことをテストで証明。Free Tier(モジュール1)は未認証で全文取得できること

### T-603 ソフトウォールUIと導線(サイズM)
- 成果物: `<ContentWall>`コンポーネント(§3.2の仕様)、フェードアウト演出、CTA(登録/サインイン/モジュール1へ)、ja/en両言語、ヘッダー・カリキュラム一覧での鍵アイコン表示
- 受入基準: verify-webapp+qa-evaluator全観点4以上。未認証/認証済みの両状態で表示が正しいこと

### T-604 演習・クイズ・検索のゲーティング(サイズM)
- 成果物: ゲート対象の演習YAML・クイズYAMLを未認証に配信しない制御、検索インデックスのゲート対象をタイトル+要約のみに制限
- 受入基準: 未認証でゲート対象の演習/クイズのデータ取得を試みた際に本体が返らないテスト。Free Tierの演習は従来どおり動作

### T-605 E2EとSEO検証(サイズM)
- 成果物: E2E(未認証でモジュール1完走 → モジュール2でウォール → 登録 → 続きが読める → ゲスト進捗がマージされている)、SEO検証(プレビュー部分がHTMLに含まれること、構造化データ、hreflang維持)
- 受入基準: 上記E2Eが3回連続成功。Lighthouse SEOスコアが実装前から低下していないこと

**依存**: T-601 →(人間の裁定)→ T-602 → T-603 ∥ T-604 → T-605

## 8. リスク

| リスク | 対応 |
|---|---|
| 動的レンダリング化でWorker invocationが無料枠を圧迫 | T-601で見積もり。超過見込みならB方式、それも厳しければPaid($5/月)への移行判断(ADR-008 §5の撤退基準に準拠) |
| ゲート導入でSEO流入が落ちる | プレビューを必ずHTMLに含める。T-605で計測 |
| Free Tierが狭すぎて登録前に離脱 | モジュール1を丸ごと開放。効果測定は運用後(現時点で分析基盤はないため定性判断) |
| 既存ユーザー(いれば)の体験が急に狭まる | 現時点で公開前のため影響なし。公開後に変更する場合は告知が必要 |
