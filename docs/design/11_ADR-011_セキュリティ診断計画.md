# ADR-010: セキュリティ診断計画(公開前アセスメント)

| 項目 | 内容 |
|---|---|
| ステータス | Proposed (2026-08-02) |
| 目的 | 公開前(07 F-1〜F-7)の一環として、本アプリの脆弱性を体系的に洗い出し、公開可否を判断できる状態にする |
| 関連 | 01 §5・§10(セキュリティ要件)、02 §7(実行エンジン)・§10、05 ADR-007、09 ADR-008(2 Worker)、10 ADR-009(アクセス制御) |

---

## 1. スコープと前提(重要)

### 1.1 実施すること
- **静的解析**: 依存関係の脆弱性、シークレット混入、コードパターン
- **設計レビュー**: 脅威モデリング(STRIDE)に基づく設計上の欠陥の洗い出し
- **ローカル/プレビュー環境での動的検証**: 認証・認可バイパス、サンドボックス脱出、XSS等を**自環境で**検証
- **設定監査**: セキュリティヘッダ、Cookie属性、CORS、Cloudflare設定

### 1.2 実施しないこと(明示的に対象外)
- **本番環境への攻撃的スキャン・侵入テスト**: 実運用環境へのスキャンはサービス停止・データ破壊・規約抵触のリスクがある。本アプリの規模と目的(公開前品質担保)には過剰であり、静的解析+ローカル動的検証で十分
- **第三者サービス(Cloudflare/Neon/GitHub/Google)自体の脆弱性調査**: 責任共有モデル上、プロバイダ側の領域
- **DDoS耐性試験**: Cloudflareが担保。自前で負荷をかける行為は規約上も不適切

### 1.3 本アプリ固有のリスク特性
| 特性 | セキュリティ上の意味 |
|---|---|
| **ユーザー投稿コードをブラウザで実行**(ADR A-01) | 本アプリ**最大の攻撃面**。サンドボックス脱出、XSS、リソース枯渇 |
| 2 Worker構成 + service binding(ADR-008) | worker-apiが直接公開されていないことが認可の前提。この前提が崩れると全API素通し |
| JWT戦略(ADR-008 T-503) | 署名検証の欠陥・アルゴリズム混同・有効期限の扱い |
| コンテンツゲーティング(ADR-009) | 未認証への情報漏洩(本文・演習定義・メタデータ経由) |
| ユーザー生成コンテンツ(ノート機能 T-307) | 保存型XSSの主要経路 |
| 教材・進捗のみ保持、決済なし | 個人情報は最小(email/表示名/学習履歴)。被害規模は限定的 |

## 2. 脅威モデル(STRIDE)

| 脅威 | 本アプリでの具体例 | 想定影響 |
|---|---|---|
| **S**poofing(なりすまし) | JWT偽造、セッション固定、OAuth stateの不備 | 他人の学習データ閲覧・改ざん |
| **T**ampering(改ざん) | 進捗/提出の不正操作、修了証の不正取得 | 修了証の信頼性喪失 |
| **R**epudiation(否認) | 監査ログの不在 | 影響小(決済なし) |
| **I**nformation disclosure(情報漏洩) | ゲート対象コンテンツ漏洩、他人のノート閲覧、シークレット露出、エラーメッセージからの内部情報漏洩 | 事業価値(教材)の毀損、プライバシー侵害 |
| **D**enial of service | 無限ループコードでのブラウザ固着、API濫用によるNeon/Worker枠消費 | サービス品質低下、コスト増 |
| **E**levation of privilege(権限昇格) | **サンドボックス脱出**(ユーザーコードからのfetch/DOM/Cookieアクセス)、他ユーザーのリソースへのIDOR | 最も深刻。セッション窃取に直結 |

## 3. 診断項目(チェックリスト)

### 3.1 【最優先】コード実行サンドボックス(02 §7.1)
本アプリ最大の攻撃面。以下を実際に攻撃コードで検証する:
| # | 検証内容 |
|---|---|
| SB-1 | Worker内から`fetch`/`XMLHttpRequest`/`importScripts`/`WebSocket`が到達不能か |
| SB-2 | `self`/`globalThis`経由での無効化APIの復元(`Object.getPrototypeOf`, `constructor`チェーン等)ができないか |
| SB-3 | `new Function`/`eval`経由でのサンドボックス外アクセス |
| SB-4 | `import()`動的インポートで外部URLを読み込めないか |
| SB-5 | 親スレッドへの`postMessage`で不正な構造を送り、メインスレッド側のパース処理を破壊できないか |
| SB-6 | 無限ループ・巨大メモリ確保でタブが固着せず、terminateが確実に効くか |
| SB-7 | Cookie/localStorage/IndexedDBへの到達不能性(Worker特性の確認) |
| SB-8 | 結果メッセージ経由でのXSS(console出力・diff表示がDOMに挿入される経路) |

### 3.2 認証・認可
| # | 検証内容 |
|---|---|
| AU-1 | JWTの署名検証(`alg: none`、アルゴリズム混同、鍵の取り違え) |
| AU-2 | JWTの有効期限・失効(ログアウト後のトークン再利用、削除済みユーザーのトークン) |
| AU-3 | Cookie属性(HttpOnly/Secure/SameSite)の実測 |
| AU-4 | **IDOR**: 他ユーザーのnote/submission/progressをID指定で取得・更新できないか |
| AU-5 | worker-apiへの直接アクセス可否(service binding前提の検証。公開ルートがないこと) |
| AU-6 | `/internal/auth/*`エンドポイントの外部到達性 |
| AU-7 | OAuth: state/PKCE、リダイレクトURIの検証、アカウントリンクの安全性 |
| AU-8 | パスワード: ハッシュ方式(ADR-007 C-3のscryptフォールバック含む)、レート制限の実効性 |
| AU-9 | ADR-009のゲーティング: 未認証で本文・演習定義・クイズ解答がレスポンスに含まれないか(RSCペイロード/metadata/OGP/検索インデックス含む) |

### 3.3 インジェクション・XSS
| # | 検証内容 |
|---|---|
| IJ-1 | **保存型XSS**: ノート(T-307)のMarkdown経由(`javascript:`URL、`<img onerror>`、DOMPurify設定の妥当性) |
| IJ-2 | 反射型XSS: 検索クエリ、エラーメッセージ |
| IJ-3 | MDXレンダリングでのHTML注入(教材はリポジトリ管理だが、コンポーネントのpropsに動的値が入る箇所) |
| IJ-4 | SQLインジェクション: Prisma使用のため低リスクだが、生SQL(`$queryRaw`)の有無を確認 |
| IJ-5 | **SQL演習(T-201)**: sql.jsはブラウザ内なので影響はローカルDBのみ。ただしsetupSqlへのユーザー入力混入経路を確認 |

### 3.4 設定・ヘッダ
| # | 検証内容 |
|---|---|
| CF-1 | CSP(Content-Security-Policy)の有無と妥当性。**Monaco/Worker/WASMを使うため`unsafe-eval`が必要になる箇所の最小化** |
| CF-2 | HSTS、X-Content-Type-Options、Referrer-Policy、Permissions-Policy |
| CF-3 | CORS設定(worker-api、静的アセット) |
| CF-4 | エラーレスポンスからのスタックトレース・内部パス漏洩 |
| CF-5 | `/lab-preview`・`/viz-preview`等の開発用ルートの本番到達性とnoindex |
| CF-6 | Sentryへの送信内容(PII/提出コードが含まれないこと。02 §10の方針準拠) |

### 3.5 依存関係・シークレット
| # | 検証内容 |
|---|---|
| DP-1 | `npm audit`(high/critical)、Dependabotアラート |
| DP-2 | リポジトリ全履歴のシークレットスキャン(`gitleaks`等) |
| DP-3 | `.env`の追跡除外、ビルド成果物へのシークレット混入(バンドル内文字列検索) |
| DP-4 | GitHub Actions: `pull_request_target`の不使用、シークレットのログ出力、third-party actionのpin |

### 3.6 レート制限・リソース枯渇
| # | 検証内容 |
|---|---|
| RL-1 | 認証エンドポイントのレート制限(T-005実装分)の実効性 |
| RL-2 | 進捗/提出APIの濫用によるNeon接続枯渇・Worker invocation消費 |
| RL-3 | 提出コード64KB制限(02 §2.1)の実効性 |

## 4. タスク分割(T-701〜T-706)

**T-701〜T-703は並列可**(触る領域が異なる)。T-704は結果を受けた修正、T-705は恒久化。

### T-701 自動化スキャン基盤の導入(サイズM)
- 成果物: `npm audit`(high以上で失敗)、`gitleaks`(全履歴)、CodeQL(GitHub Actions)、`semgrep`(任意)をCIに追加。既存の検出結果を一覧化
- 受入基準: CIで各スキャンが動作し、現時点の検出結果(件数と内容)が報告される。**検出ゼロを目指して設定を緩めることは禁止**(実際の指摘は正直に報告)
- Out of Scope: 検出された脆弱性の修正(T-704)

### T-702 サンドボックス侵入テスト(サイズL)【最優先】
- 成果物: §3.1のSB-1〜8を検証する**実際の攻撃コード**をテストとして実装(`tests/security/sandbox-escape.test.ts`)。各攻撃が失敗する(=防御が効く)ことをテストで固定
- 受入基準: 8項目全ての検証コードが存在し、防御が効いていることが自動テストで証明される。**突破できた項目があれば、それを隠さず報告し、修正は行わずT-704へ回す**
- 注意: 攻撃コードは`tests/security/`配下に限定し、本番バンドルに含まれないことを確認

### T-703 認証・認可・情報漏洩の検証(サイズL)
- 成果物: §3.2(AU-1〜9)と§3.3(IJ-1〜5)の検証。特にIDOR(他ユーザーIDでのAPI操作)とゲーティング漏洩(RSCペイロード/metadata/検索インデックス)を実リクエストで検証するテスト
- 受入基準: 各項目の検証結果表。突破できた項目は報告のみ(修正はT-704)
- 検証環境: `npm run preview`(実workerd)+ `workers/api`の`wrangler dev`

### T-704 セキュリティヘッダとCSPの整備(サイズM)
- 成果物: §3.4(CF-1〜6)の実装。特にCSPは**Monaco/Web Worker/WASMが動作する最小権限**を実測しながら構築
- 受入基準: 主要ページでCSP違反コンソールエラーがゼロかつ演習が動作すること。securityheaders.com相当の自己評価結果を報告

### T-705 検出脆弱性の修正(サイズは検出結果次第 / T-701〜704完了後)
- 成果物: T-701〜704で検出された問題の修正。深刻度順(Critical/High → Medium → Low)
- 受入基準: 修正した各項目について、T-702/703で追加した攻撃テストが「防御成功」に転じることを証明

### T-706 セキュリティ運用の恒久化(サイズS)
- 成果物: `SECURITY.md`(脆弱性報告窓口)、CIへのセキュリティゲート常設、依存更新方針(Dependabot設定)、`.claude/skills/`へのセキュアコーディング指針追記
- 受入基準: 07(人間作業チェックリスト)のGセクションに週次のセキュリティ確認項目が追加提案されている(ファイル編集は人間が実施)

## 5. 深刻度の判定基準と公開可否

| 深刻度 | 定義 | 公開可否 |
|---|---|---|
| **Critical** | サンドボックス脱出、他ユーザーデータの取得・改ざん、シークレット漏洩、認証バイパス | **公開不可**。修正必須 |
| **High** | 保存型XSS、ゲート対象コンテンツの全文漏洩、レート制限の完全な不在 | 公開不可。修正必須 |
| **Medium** | セキュリティヘッダ欠如、情報漏洩(スタックトレース等)、依存パッケージのhigh脆弱性 | 公開前に修正が望ましい。リスク受容する場合は理由を記録 |
| **Low** | ベストプラクティスからの逸脱、影響の限定的な情報漏洩 | 記録し、公開後に対応可 |

**07 F-1〜F-7(公開前チェックリスト)にF-8「セキュリティ診断でCritical/High がゼロであること」を追加する。**

---

## 6. 診断結果の取り扱い(重要)

- 検出された脆弱性の詳細は**公開リポジトリのPR本文やIssueに書かない**。`docs/security/findings.md`(gitignore対象)またはプライベートな記録に留め、PRには「T-704の指摘Aを修正」のように参照のみ記載する
- 攻撃テストコード自体は防御の回帰テストとして価値があるため、`tests/security/`にコミットしてよい(ただし本番バンドル非混入を確認)
- 修正前の脆弱性が特定できる情報を、修正がマージされる前に公開しない
