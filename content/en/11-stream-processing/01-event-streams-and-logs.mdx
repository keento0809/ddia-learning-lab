# Event Streams and Logs

The previous modules mostly dealt with request-driven processing: a request
comes in, you read or write some data, and you send back a response. In
practice, though, a different shape of processing comes up just as often:
"whenever something happens, keep telling every interested party about that
fact afterward." An order was placed, a sensor reading was updated, a user
viewed a page — treating this kind of chain of "things that happened" as an
<Term slug="event-stream">event stream</Term> is the starting point for the
stream processing this module covers.

## Events versus batch processing

Batch processing is bounded: it processes whatever data has accumulated by a
given point in time, and then waits for the next batch. Stream processing,
by contrast, keeps processing an unbounded (potentially endless) sequence of
events a little at a time, as they occur.

- **Batch processing**: once a day, aggregate yesterday's order log in one go
- **Stream processing**: as soon as an order is placed, immediately reflect
  it in inventory and dashboards

Neither one is simply "better" — the choice is a tradeoff driven by how
quickly you need the result and how bounded the input actually is.

<Callout type="info">
  Stream processing doesn't replace batch processing. In practice, it's
  common to design the same aggregation logic so it can run both ways: "run
  it in bulk over historical data (batch)" and "update it incrementally as
  new events arrive (stream)."
</Callout>

## The event stream as a log

One way to implement an event stream is an
<Term slug="event-log">event log</Term>, an append-only data structure. New
events are always added at the end, and existing events are never modified.
This simple property brings several benefits.

- **Order is preserved**: the order within the log is (approximately) the
  order the events occurred in
- **Multiple readers stay independent**: each consumer only needs to
  remember how far it has read, with no effect on any other consumer's
  progress
- **You can read it again later**: adding a new consumer lets it replay from
  the start of the log and pick up past events too

The value each consumer keeps to track "how far along have I read" is called
a <Term slug="consumer-offset">consumer offset</Term>. Because consumers
manage their own offsets, multiple consumer groups running at different
speeds can each read through the same log at their own pace without
interfering with one another.

## How this differs from a traditional message queue

Many traditional <Term slug="message-queue">message queues</Term> are
designed so that once a message is delivered to one consumer (and
acknowledged), it's removed from the queue. That's well suited to
distributing tasks across workers, but it's a bit awkward for a different
goal: delivering the same event independently to several consumers that
each want it for a different purpose.

In the log-based approach, messages stay in the log for some period (or up
to some size), and multiple consumer groups each read the same log with
their own independent offset. This naturally gives you fan-out: one event
stream can feed several different downstream uses at once — inventory
updates, analytics, and audit logging, for example.

<Callout type="warn">
  Logs normally have a limit on how long or how much they retain. If one
  consumer's processing stalls for a long time, the old events it still
  needs to read may get deleted from the log and become unreplayable. When
  designing a stream processing system, you need to deliberately decide on a
  retention period that tolerates a consumer being down for some amount of
  time.
</Callout>
