# ネットワーク分断と非同期ネットワークの現実

同じプロセス内の関数呼び出しは、成功するか例外を投げるかのどちらかであり、
結果が「わからないまま」になることはまずありません。しかし複数のマシンが
ネットワーク越しに協調して動く分散システムでは、事情がまったく異なります。
リクエストを送っても応答が返ってこないとき、何が起きたのかを送信側だけの
情報から確定させることはできません。

## 非同期ネットワークの前提

一般的なデータセンター内ネットワークやインターネットは、
<Term slug="asynchronous-network">非同期ネットワーク</Term>としてふるまいます。
つまりメッセージがどれだけの時間で届くか、そもそも届くかどうかについて、
上限を保証する仕組みがありません。具体的には次のようなことが日常的に起こり得ます。

- パケットがスイッチやルーターのキューで待たされ、遅延する
- 輻輳やハードウェア障害でパケットが再送されずに失われる
- パケットの到着順序が送信順序と入れ替わる
- ケーブル抜けや設定ミスで、一時的に経路そのものが失われる

これらは「めったに起きない例外」ではなく、大規模なシステムを長期間運用すれば
必ず発生する通常運転の一部として設計に織り込む必要があります。

## 応答が来ないとき、何が起きたのか

クライアントがサーバーにリクエストを送り、一定時間たっても応答が返らない
状況を考えます。この時点でクライアントが知っている情報だけでは、
次のどのケースが起きているのか区別できません。

```
ケースA: リクエスト自体が届いていない
  Client                     Server
    |--- request -----X      |   (パケット喪失)
    |  (応答を待ち続ける)     |

ケースB: サーバーは処理して応答したが、応答が届かない
  Client                     Server
    |--- request ----------->|
    |         X<------ response|  (応答パケットが喪失)

ケースC: サーバーが処理に非常に時間がかかっている
  Client                     Server
    |--- request ----------->| (処理中、まだ終わっていない)
    |      (応答待ち)         |

ケースD: サーバーが停止している
  Client                     Server
    |--- request ----------->| (プロセスが落ちている/応答不能)
```

ケースAとDでは「相手は動いていない」という判断が結果的に正しいことも
ありますが、ケースB・Cでは相手は正常に動いている(あるいは動いていた)
にもかかわらず、クライアント側からは区別がつきません。この非対称性が、
分散システムの障害検知を本質的に難しくしています。

<Callout type="info">
  同一データセンター内のネットワークでも、非同期ネットワークの前提を完全には
  免れません。輻輳やハードウェア障害は稀にせよ発生するため、「信頼できる
  ネットワーク」を前提にした設計は本番運用のどこかで破綻します。
</Callout>

## ネットワーク分断とその影響

<Term slug="network-partition">ネットワーク分断</Term>
とは、スイッチの故障や設定ミス、極端な輻輳などにより、ノード群が複数の
グループに分かれて相互に通信できなくなる状態を指します。分断が起きても
各グループの内部では通信が正常に行えることが多く、それぞれのグループが
「自分たちは正常で、相手側が落ちている」と認識してしまうことがあります。

<Callout type="warn">
  分断中に両側が独立して書き込みを受け付け続けると、後で分断が解消した際に
  矛盾したデータをどう統合するかという問題が生じます(スプリットブレイン)。
  この問題への具体的な対処(クォーラムやリーダー選出など)は、後続モジュールの
  合意アルゴリズムの範囲で扱います。
</Callout>

## タイムアウトという苦渋の選択

メッセージの到達に保証がない以上、実務上は「一定時間応答がなければ相手は
停止しているとみなす」というタイムアウトによる推測で折り合いをつけるしか
ありません。ここには次のようなトレードオフがあります。

- **タイムアウトを短くする**: 障害を素早く検知できる一方、実際には動いている
  ノードを停止と誤判定する
  <Term slug="false-positive-detection">誤検知(フォールスポジティブ)</Term>
  が増える
- **タイムアウトを長くする**: 誤検知は減るが、本当に停止したノードの検知が
  遅れ、利用者が待たされる時間が伸びる

「絶対に正しいタイムアウト値」は存在せず、想定されるネットワーク遅延の分布や
許容できる誤検知率をもとに、意図を持って選び取る設計判断になります。この
考え方は本モジュールの演習(安全なタイムアウト値の算出)で実際に手を動かして
確認します。
