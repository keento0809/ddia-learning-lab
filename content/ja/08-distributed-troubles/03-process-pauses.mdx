# プロセス停止という落とし穴

分散システムの障害検知は「一定時間ハートビートが来なければ、そのノードは
停止した」という考え方に大きく依存しています。しかし実際には、ノードの
プロセス自体は生きていながら、OSやランタイムの都合で長時間「応答できない
状態」に陥ることがあります。この章では、プロセスが予期せず一時停止する
主な原因と、それが分散システムの正しさに与える影響を整理します。

## プロセスが一時停止する主な原因

- **<Term slug="gc-pause">GCポーズ</Term>**: ガベージコレクションの実行中、
  多くのランタイムではアプリケーションスレッドが一時的に停止します
  (いわゆるストップ・ザ・ワールド)。ヒープサイズや生存オブジェクト数、
  GCアルゴリズムによっては、停止時間が数百ミリ秒から数秒、極端な場合は
  それ以上に及ぶことがあります
- **OSレベルのスケジューリング遅延**: 他のプロセスとのCPU競合や、
  ハイパーバイザー上での他の仮想マシンとの競合により、実行が長時間
  後回しにされることがあります
- **ページフォールト・スワップ**: メモリが不足している環境では、
  ディスクI/Oを伴うページフォールトによって処理が数十ミリ秒から
  それ以上停止することがあります
- **ノートPCのスリープ・仮想マシンのライブマイグレーション**: 開発環境や
  一部の運用環境では、プロセスそのものが数秒から数分単位で完全に
  停止することがあります

これらはいずれも「プロセスがクラッシュした」わけではなく、一定時間の
のちに何事もなかったかのように処理を再開します。しかし停止していた
本人はどれだけの時間が経過したかを実行中に知る術がなく、周囲のノードから
見れば「ハートビートが途絶えた=停止した」と判断されるのに十分な時間
かもしれません。

```
タイムライン(ノードNのGCポーズが原因で起きる問題の例)

t=0    ノードNがリース(利用権)を取得。有効期限はt=10
t=1    ノードNで長時間のGCポーズが発生(本人は気づかない)
t=11   他のノードが「リースが切れた」と判断し、新たにリースを取得して処理開始
t=13   ノードNのGCポーズが終了。N自身はまだt=1の続きのつもりで処理を再開
       → この時点でNと新しいリース保持者が同じ資源に同時に書き込みうる
```

## リースやロックへの影響

上記のようなタイムラインは、分散ロックやリース(有効期限付きの利用権)を
扱うシステムで特に注意が必要です。停止から復帰したノードは、自分が
リースを失ったことに気づかないまま処理を続けてしまう可能性があり、
そのまま新しいリース保持者と競合した書き込みを行えば、データの不整合を
引き起こしかねません。

<Callout type="warn">
  「リースの有効期限が切れていないかをアプリケーションコードでチェックしてから
  書き込む」という対策は、チェックした直後にまさにその一時停止が起きれば
  意味をなさなくなります。チェックと実際の書き込みの間に時間差がある限り、
  この種の競合を完全には防げません。
</Callout>

## 緩和策の考え方

完全に一時停止を防ぐことは現実的ではないため、実務では次のような
考え方で影響を抑えます。

- <Term slug="fencing-token">フェンシングトークン</Term>: リースを取得するたびに単調増加するトークンを
  発行し、資源側(ストレージなど)がそのトークンを検証して、古いトークンを
  使った書き込みを拒否する。これにより、一時停止から復帰した古いリース
  保持者が誤って書き込んでも、資源側で弾くことができる
- **タイムアウト・リース期間の設計**: 想定される最大の一時停止時間
  (典型的なGCポーズの長さなど)を踏まえて、リース期間やハートビートの
  タイムアウトに十分な安全マージンを持たせる
- **一時停止の監視**: GCポーズの長さや頻度を監視し、閾値を超えた場合に
  アラートを上げる運用を組み合わせる

これらは「一時停止が絶対に起きない」ことを保証する対策ではなく、
「一時停止が起きても致命的な不整合につながらない」ように設計する
考え方である点が重要です。
