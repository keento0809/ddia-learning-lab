# バッチ処理とMapReduceの基本モデル

ここまでのモジュールでは、ユーザーからのリクエストに即座に応答する
オンラインシステム(サービス型システム)を主に扱ってきました。しかし
実世界のデータシステムには、もう一つ重要な系統があります。大量の
データをまとめて読み込み、集計・変換・分析した結果を後で使えるように
書き出す<Term slug="batch-processing">バッチ処理</Term>です。

## バッチ処理とオンライン処理の違い

オンラインシステムはリクエストが来るたびに低レイテンシで応答する必要が
あり、1件ごとの処理が遅れることが直接ユーザー体験の悪化につながります。
一方バッチ処理は、あらかじめ蓄積された(あるいは一定期間分まとまった)
入力データ全体を対象に、まとめて処理を実行します。

- 個々のリクエストへの即時応答は求められない代わりに、数百GB〜数TB規模の
  入力を扱えるスループットが求められる
- 処理時間は秒単位ではなく分〜時間単位で許容されることが多い
- 典型的な用途: 日次の売上集計、ログからのレポート生成、検索インデックスの
  再構築、機械学習の特徴量やモデルの再計算 など

<Callout type="info">
  「バッチ」と「ストリーム」はどちらもオンラインの即時応答系とは異なる処理
  形態ですが、バッチは有限の入力(ある時点で区切られたデータ集合)を対象に
  するのに対し、ストリームは終わりのないイベント列を継続的に処理します。
  ストリーム処理は後続モジュールで扱います。
</Callout>

## なぜ1台では足りないのか

バッチ処理の対象データが1台のマシンのメモリやディスクI/O帯域に収まらない
規模になると、複数マシンに処理を分散する必要が出てきます。単純に分散
させるだけなら「入力を適当に分割して各マシンに投げる」という発想でも
よさそうですが、実務では次のような課題が繰り返し現れます。

- 入力データを、意味のある単位でどう分割してマシンに割り当てるか
- 各マシンの計算結果を、最終的にどうやって1つの答えへ統合するか
- 数百台規模のクラスタでは、処理の途中でどこかのマシンが必ず落ちる
  (障害耐性をどう組み込むか)

<Term slug="mapreduce">MapReduce</Term>は、この種の分散バッチ処理を
「map」「shuffle」「reduce」という3つの汎用的な段階に定式化することで、
上記の課題に共通の答えを与えるプログラミングモデルです。

## map・shuffle・reduceの3段階

1. **map段階**: 入力データをレコード単位(例: ログの1行、ドキュメント1件)
   で読み込み、各レコードから0個以上の「キーと値のペア」を生成する。
   map関数は各レコードを独立に処理でき、他のレコードの状態を必要としない
   ため、入力を好きなだけ細かく分割してマシン間で並列に実行できる
2. **<Term slug="shuffle-phase">シャッフル段階</Term>**: mapが出力した
   大量のキー・値ペアを、同じキーを持つペア同士が同じマシン(reduce
   タスク)に集まるように、クラスタ全体でネットワーク越しに再配置する
3. **reduce段階**: 1つのキーに対応するすべての値をまとめて受け取り、
   それらを集約して最終的な出力を生成する

この分割により、mapとreduceはそれぞれ独立して大量に並列実行でき、
「同じキーの値を1箇所に集める」という本質的に難しい部分だけをシャッフル
段階に切り出せます。

## 具体例: 単語の出現回数を数える

MapReduceの説明で定番の題材である単語カウント(word count)を考えます。
複数の文書が入力として与えられ、単語ごとの出現回数を数えたいとします。

```
入力ドキュメント:
  doc1: "the cat sat"
  doc2: "the cat ran"

map段階の出力(各ドキュメントから単語ごとに (単語, 1) を生成):
  ("the", 1) ("cat", 1) ("sat", 1)
  ("the", 1) ("cat", 1) ("ran", 1)

シャッフル段階(同じキーの値を1箇所に集約):
  "the" -> [1, 1]
  "cat" -> [1, 1]
  "sat" -> [1]
  "ran" -> [1]

reduce段階(キーごとに値を合計):
  "the" -> 2
  "cat" -> 2
  "sat" -> 1
  "ran" -> 1
```

map関数は「1単語ごとに (単語, 1) を出力する」という単純な処理しか
行っておらず、実際に集計を行うのはreduce関数です。この役割分担こそが
MapReduceの核心で、mapは入力を読みながらいくらでも並列化でき、reduceは
シャッフルによって同じキーの値がすでに集約された状態から仕事を始められます。

<Callout type="tip">
  本モジュールの演習「ミニMapReduce実装」では、この単語カウントの
  map・shuffle・reduceの各段階を実際にJavaScriptの関数として実装し、
  複数ドキュメントに対して動かして確認します。
</Callout>

## mapとreduceが満たすべき性質

MapReduceのモデルが分散環境でうまく機能するのは、map関数・reduce関数に
次のような制約を課しているためです。

- **他のレコードの状態に依存しない**: mapは1レコードだけを見て出力を
  決められる(だからこそ入力を自由に分割して並列化できる)
- **決定的である**: 同じ入力に対しては常に同じ出力を返す(この性質が
  なぜ重要かは、本モジュール後半の耐障害性の回で詳しく扱う)
- **副作用を持たない**: 外部のデータベースを書き換えるなど、関数の外の
  状態を変えない(出力はフレームワークが管理する場所へまとめて書き出す)
