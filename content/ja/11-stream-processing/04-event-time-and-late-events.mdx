# 時刻の扱いと遅延イベント

前レッスンのウィンドウ集計の骨格は、「イベントは発生した順番どおりに、
遅れなく処理システムへ届く」ことを暗黙に前提にしていました。しかし
実際のシステムでは、モバイル端末がオフラインの間に発生したイベントが
まとめて後から送られてきたり、ネットワークの混雑で一部のメッセージだけ
遅延したりすることが日常的に起こります。この「いつのイベントか」と
「いつ処理されたか」のずれを正しく扱うことが、ストリーム処理の実務上の
難所です。

## イベント時刻と処理時刻

<Term slug="event-time">イベント時刻</Term>は、そのイベントが実際に
発生した時刻(センサーが値を読み取った瞬間、ユーザーがクリックした瞬間など)
です。一方、<Term slug="processing-time">処理時刻</Term>は、そのイベントが
ストリーム処理システムに届いて実際に処理された時刻です。

- クライアント側でイベントを生成してから送信するまでの遅延
- ネットワーク経由の転送にかかる時間
- 一時的な障害やオフライン状態によるリトライ・再送

これらの要因により、処理時刻は常にイベント時刻と同じか、それより後になり、
かつそのずれの大きさはイベントごとにばらつきます。「直近1分間のイベント数」
を集計したいとき、その「1分間」がイベント時刻を基準にした1分間なのか、
処理時刻を基準にした1分間なのかによって、同じ実装でも結果が変わり得ます。

<Callout type="warn">
  処理時刻を基準にウィンドウを区切ると、実装は単純になりますが「同じ入力
  データを別のタイミングで再処理すると異なる集計結果になる」という問題が
  起こります。障害からの復旧時にストリームを再生(リプレイ)して集計を
  やり直す場合など、再現性が求められる場面ではイベント時刻を基準にする方が
  望ましいことが多いです。
</Callout>

## いつまで待てばよいのか、という問題

イベント時刻を基準にウィンドウを区切ると決めても、新しい問題が生じます。
「あるウィンドウに属するイベントがもう全部揃った」と、いつ判断すれば
よいのでしょうか。理論上は「そのウィンドウの終了時刻より前のイベント時刻を
持つイベントが、まだ後から届くかもしれない」という可能性を完全には
排除できません。

実務では、この問題に「無限に待ち続けるわけにはいかない」という現実的な
判断で折り合いをつけます。その仕組みが
<Term slug="watermark">ウォーターマーク</Term>です。ウォーターマークとは、
「これより前のイベント時刻を持つイベントは、もう届かないとみなしてよい」
という処理システム側の推測を表す時刻の指標です。典型的には、これまでに
観測したイベント時刻の最大値から、許容する遅延の上限を差し引いた値として
計算されます。

```
ウォーターマーク = これまでに観測した最大のイベント時刻 - 許容遅延

例: 許容遅延を30秒とする
  観測した最大のイベント時刻が 10:05:40 なら
  ウォーターマークは 10:05:10
  → 10:05:10 より前のイベント時刻を持つウィンドウは確定させてよい、とみなす
```

## 遅延イベントの扱い方

ウォーターマークがウィンドウの終了時刻を追い越した後に、そのウィンドウに
属するはずのイベントが届くことがあります。これを
<Term slug="late-arriving-event">遅延到着イベント</Term>と呼びます。
遅延イベントへの典型的な対処にはいくつかの選択肢があります。

- **破棄する**: 単純だが、その分だけ集計結果が実際の値より少なくなる
- **許容遅延を長く取る**: 遅延イベントを取りこぼしにくくなるが、
  ウィンドウの確定(=結果を利用可能にする)までの時間が伸びる
- **確定後の再訂正を許す**: 一度確定したウィンドウの集計結果を、遅延
  イベントの到着に応じて後から更新する。正確さは増すが、「集計結果は
  後から変わることがある」という前提を下流のシステムにも持たせる必要がある

<Callout type="tip">
  「許容遅延をどれだけ取るか」は、タイムアウト値の設計(モジュール8)と
  よく似たトレードオフです。許容遅延を長くすれば取りこぼしは減りますが
  結果が出るまでの待ち時間が伸び、短くすれば結果は早く出ますが遅延イベントを
  失いやすくなります。「絶対に正しい値」ではなく、実際に観測される遅延の
  分布と、求められる鮮度のバランスから決める設計判断です。
</Callout>

本モジュールの演習「ストリーム集計ラボ」では、タンブリングウィンドウの
集計に加えて、ここで説明したウォーターマークの考え方を使い、遅延イベントが
実際にどう扱われるかを手を動かして確認します。
