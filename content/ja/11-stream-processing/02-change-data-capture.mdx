# チェンジデータキャプチャ(CDC)

多くのシステムでは「正」となるデータはリレーショナルデータベースに
保存されています。しかし検索インデックスの更新、キャッシュの無効化、
分析基盤への連携など、データベースの変更を他のシステムにも反映したい
場面は数多くあります。<Term slug="change-data-capture">CDC(チェンジデータ
キャプチャ)</Term>は、データベースへの書き込みをイベントストリームとして
取り出す手法の総称です。

## なぜアプリケーションコードから直接送らないのか

一見、アプリケーションコードが「DBへの書き込み」と「イベントの送信」を
両方自分で行えばよいように思えます。しかしこの「二重書き込み
(デュアルライト)」には根本的な問題があります。

```
アプリケーションコード:
  1. データベースに書き込む
  2. イベントストリームにメッセージを送る
```

この2つの操作は別々のシステムへの別々の書き込みであるため、
片方だけが成功してもう片方が失敗する状況を避けられません。プロセスが
ステップ1と2の間でクラッシュすれば、DBには変更が反映されているのに
イベントは誰にも送られていない、という不整合が生じます。

<Callout type="warn">
  「先にDBに書いて、成功したらイベントを送る」という順序にしても、
  イベント送信の失敗やプロセスクラッシュのタイミング次第で不整合は起こり得ます。
  二重書き込みを「がんばって両方成功させる」方向で解決しようとするのではなく、
  そもそも二重書き込みをしない設計にするのがCDCの発想です。
</Callout>

## ログベースCDC: 変更を後から拾い出す

多くのデータベースは、内部的にすべての変更をあらかじめ
<Term slug="event-log">追記専用のログ</Term>(例: 先行書き込みログ)に
記録してからテーブルへ反映しています。ログベースCDCは、この既存のログを
外部から読み取り、行の挿入・更新・削除をイベントストリームへ変換します。

- アプリケーションコードは通常どおりDBへ書き込むだけでよい(二重書き込みが不要)
- DBが書き込みを確定させた時点で、変更は必ずログに残っている
- CDCの仕組みはそのログを読んで配信するだけなので、アプリケーションの
  トランザクションと独立して動く

この方式では、CDCの読み取りプロセスが一時的に遅れても、DB側のログが
保持されている限り追いつくことができます。ただし前レッスンのイベントログと
同様、ログの保持期間には限りがあるため、CDCプロセスが長時間止まると
変更を取りこぼす可能性があります。

## アウトボックスパターン

データベース内部のログに直接アクセスする権限がない、あるいは複数種類の
データストアにまたがる変更をまとめて配信したい場合には、
<Term slug="outbox-pattern">アウトボックスパターン</Term>がよく使われます。

1. アプリケーションは、本来のデータ更新と「送信すべきイベント」の記録を
   **同じデータベーストランザクション内**で行う(専用の「アウトボックス」
   テーブルに書き込む)
2. 別プロセスがアウトボックステーブルを定期的に読み取り、外部の
   イベントストリームへ配信する
3. 配信済みのレコードには印を付ける(または削除する)

この方式のポイントは、「本来のデータ」と「送るべきイベント」の書き込みを
同じトランザクションにまとめることで、二重書き込み問題を1つのデータストアの
中の単一トランザクションの問題に還元している点です。単一のデータベース
トランザクションであれば、原子性(オールオアナッシング)を保証しやすくなります。

<Callout type="tip">
  アウトボックスパターンは、DB内部のログを直接読む権限が必要なログベースCDCと
  違い、アプリケーション層だけで実装できるため、マネージドデータベース
  サービスなど内部ログへのアクセスが制限されている環境でも使いやすい
  という実務上の利点があります。
</Callout>

## CDCがもたらす設計上の変化

CDCによってデータベースの変更をイベントストリームとして扱えるようになると、
検索インデックスやキャッシュ、集計用のマテリアライズドビューなどの
「派生データ」を、元のデータベースへの変更に追従させ続けることが
自然な形で実現できます。この「イベントストリームを介してデータを
複数の形に派生させていく」という考え方は、本モジュール後半で扱う
ウィンドウ集計とも密接につながっています。
