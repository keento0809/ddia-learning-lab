# ウィンドウ集計

イベントストリームは終わりなく流れ続けるため、「全イベントの合計」のような
集計をそのまま計算し続けることはできても、「直近5分間のリクエスト数」
「1分ごとのエラー件数」のような、時間で区切った集計はそのままでは
表現できません。ストリーム処理では、こうした時間の区切りを
<Term slug="tumbling-window">ウィンドウ</Term>という単位で扱います。

## なぜウィンドウで区切るのか

無限に続くストリームに対して「今までの合計」を1つの数値として持ち続ける
ことはできますが、それだけでは「直近の傾向」を捉えられません。例えば
システム全体の累計リクエスト数が1億件あっても、直近1分間に急増している
エラー率のようなものは別途知りたいはずです。ウィンドウ集計は、
ストリームを時間軸で区切ったまとまり(ウィンドウ)ごとに集計を行うことで、
「いつ」「どれくらい」起きたかを追跡できるようにします。

## タンブリングウィンドウ

<Term slug="tumbling-window">タンブリングウィンドウ</Term>は、
固定長で互いに重ならないウィンドウです。例えば幅1分のタンブリングウィンドウ
であれば、`00:00〜00:01`、`00:01〜00:02`、`00:02〜00:03` ...と、
隙間なく連続するが重複しない区間に分割されます。あるイベントは、
そのイベント時刻がちょうど収まる1つのウィンドウにのみ属します。

```
時刻:      0    1    2    3    4    5   (分)
タンブリング [--A--][--B--][--C--][--D--][--E--]
```

タンブリングウィンドウの実装は比較的単純です。イベントの時刻を
ウィンドウ幅で割った商から、そのイベントが属するウィンドウの開始時刻を
一意に計算できます(`windowStart = floor(timestamp / windowSize) * windowSize`)。
この性質のおかげで、イベントをウィンドウごとのバケツに振り分けるだけで
集計できます。

## スライディングウィンドウ

<Term slug="sliding-window">スライディングウィンドウ</Term>は、
ウィンドウの幅とは別に「どれだけの間隔でウィンドウをずらすか(ステップ幅)」
を持ち、隣接するウィンドウが重なり合うことを許すウィンドウです。例えば
「幅5分のウィンドウを1分ごとにずらす」場合、`00:00〜00:05`の次は
`00:01〜00:06`というように、1つのイベントが複数のウィンドウに同時に
属することになります。

```
時刻:      0    1    2    3    4    5    6   (分)
スライディング [------A------]
               [------B------]
                    [------C------]
```

スライディングウィンドウは「直近5分間の移動平均を1分ごとに更新したい」
といった、滑らかに変化する指標を見たい場合に向いています。一方で
1件のイベントが複数のウィンドウの計算に影響するため、タンブリング
ウィンドウよりも保持すべき状態や計算量が増える傾向があります。

<Callout type="info">
  どちらのウィンドウ方式を使うかは「知りたい粒度」と「計算コスト」の
  トレードオフです。単純な時間帯別の集計(1時間ごとの売上合計など)には
  タンブリングウィンドウで十分なことが多く、変化を滑らかに追いたい
  監視系のメトリクスにはスライディングウィンドウが好まれる傾向があります。
</Callout>

## 集計ロジックの骨格

ウィンドウ集計の実装は、次のような形に単純化できます。

<CodeBlock lang="js">
{`function tumblingWindowSums(events, windowSizeMs) {
  const buckets = new Map();
  for (const event of events) {
    const windowStart =
      Math.floor(event.timestampMs / windowSizeMs) * windowSizeMs;
    const bucket = buckets.get(windowStart) ?? { windowStart, sum: 0 };
    bucket.sum += event.value;
    buckets.set(windowStart, bucket);
  }
  return [...buckets.values()].sort((a, b) => a.windowStart - b.windowStart);
}`}
</CodeBlock>

この骨格は「イベントが到着した順序どおりに、しかも遅れなく全部届く」
という前提を置いています。しかし実際のストリームでは、ネットワーク遅延
などによってイベントが「本来のイベント発生時刻」より遅れて届くことが
避けられません。次のレッスンでは、この「時刻のずれ」がウィンドウ集計に
どう影響するかを扱います。本モジュールの演習「ストリーム集計ラボ」では、
ここで見た骨格を実際に実装し、遅延イベントを考慮した集計にも取り組みます。
